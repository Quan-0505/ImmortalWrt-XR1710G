# RCA：1710 代理吞吐上限约 550 Mbps —— 根因是 4 核 A53 算力，不是配置

**日期**：2026-10-09
**设备**：Gemtek XR1710G / Airoha AN7581GT / 4×Cortex-A53 @ 1300 MHz / ImmortalWrt kernel 6.18.52
**现象**：1000 Mbps 线路上，直连能跑满（NPU 卸载），代理峰值 370-567 Mbps 且会掉到 200+，CPU「看起来没吃满」。

---

## 一、结论（先看这个）

```
路径                      吞吐                 CPU
────────────────────────────────────────────────────────────
直连（走 NPU 卸载）        960 Mbps  ✅ 跑满     几乎不参与（~0.25 核）
代理（走用户态 daed）      峰值 536-567 Mbps     四核合计 3.82-3.86 / 4.00  ← 满载
```

**代理上限 ≈ 550 Mbps，由 4 核 Cortex-A53@1.3GHz 的总算力决定。**

**这不是配置错误、不是限速、不是丢包、不是 daed 的 bug。**
代理流量必须逐包做协议处理（加解密），**物理上无法卸载给 NPU** ——
而 OPNsense 是 x86，单核性能约为 A53 的 3-5 倍，所以它能跑 800-1000 Mbps。

---

## 二、「CPU 没吃满」的真相（这是本项目最容易误判的一点）

用户与我都观察到「CPU 没有吃满」，因为 **htop 里没有任何一个核到 100%**。
实测账本（25 个高负载采样，平均 395 Mbps，峰值 536 Mbps）：

```
四核合计 = 3.86 核  (97% of 4)     ← 实质满载
  ├─ softirq  1.48 核  (38%)       网络软中断
  ├─ system   1.18 核  (31%)       daed 的 socket 收发计在内核态
  ├─ user     0.38 核  (10%)
  └─ daed     1.40 核  (占合计 36%)
```

**⇒ CPU 按核算是 97% 满的，只是工作被摊到 4 个核、5-6 条线程上，
所以没有任何单一指标看起来「满了」。**

**判据**：不要看「单核是否到 100%」，要看 **四核合计核数 / 4**。
四核满载 = 4.00 核。超过 3.8 即为满载。

## 三、我在这轮排查中犯的三个「口径错误」（都是同一类）

这三个错误每一个都曾让我得出错误结论，记下来避免重犯。

### 错误 1：用「累计平均」当瞬时吞吐

```sh
# 错：
printf "%.1f", (b-a)*8/1000000/(k*4)      # k*4 = 从开始到现在的秒数
```

第一次看到 `959.9 → 497.2 → 331.8 → 249.3 → 199.9 → 166.9` 以为是掉速。
还原累计字节才发现：**480 MB 在头 4 秒就下完了**，之后是**没有数据**，不是掉速。
真实瞬时吞吐 = 480 MB / 4 s = **960 Mbps**。

**⇒ 指标必须是「区间差值 ÷ 区间时长」，绝不是「累计量 ÷ 累计时长」。**

### 错误 2：用「累计 squeeze 比例」判读 netdev_budget

（上一轮遗留）`/proc/net/softnet_stat` 的累计 squeeze 比例含修复前时段，修好后仍显示 18-19%。
**必须看增量。**

### 错误 3：用「名义采样间隔」当分母

```sh
sleep 2                                   # 名义 iv = 2
# 但每轮还要跑 3 次 awk + 4 次文件复制 ⇒ 实测间隔 2.5-3.4 秒
```

后果：吞吐与 CPU 全部虚高约 25-70%。
实测出现「四核合计 = 6.93 核」——**设备只有 4 核，这本身就是 bug 的信号**。

**⇒ 修法：用 `/proc/uptime` 做时基，分母取实测间隔。**

```sh
now() { awk '{print $1}' /proc/uptime; }   # 开机秒数，精度 10ms
T0=$(now); sleep $IVT; T1=$(now)
# 所有速率的分母 = T1 - T0
```

## 四、正向对照（每次测量前必做）

**没有正向对照的测量不可信。本轮做了两个：**

| 对照 | 做法 | 期望 | 实测 |
|---|---|---|---|
| 四核公式与单位 | 每核起一个忙循环，跑 10 秒 | 四核合计 ≈ 4.00，且落在 `user` 列 | **3.98 / 4.00 / 4.00** ✅ |
| TCP snmp 字段索引 | 制造下载流量，看列是否增长 | `OutSegs` 应增长 | **+1300** ✅ |

**没有这两个对照，我会把「公式错」当成「设备没负载」。**

## 六、账本分解（为什么是这个上限）

```
总 3.86 核 = daed 1.40 核 (36%) + 网络软中断 1.48 核 (38%) + 其他系统 0.98 核 (25%)

每 Mbps 总开销 ≈ 3.86 / 395 ≈ 0.0098 核
按峰值时刻效率：536 Mbps / 3.86 核 ≈ 139 Mbps/核
⇒ 要跑 1000 Mbps 需要约 7.2 核 —— 设备只有 4 核
```

**反推每包开销（这个数字不正常，说明还有优化空间）：**

```
536 Mbps ÷ 1400 字节 ≈ 47,900 pps
1.48 核 × 1.3 GHz = 1.92 G 周期/s
1.92e9 ÷ 47,900 ≈ 40,000 周期/包      ← 正常 Linux 转发是 200-500 周期/包
```

**⇒ 软中断（38%）比 daed 本身（36%）还多，是有价值的优化方向，
但本轮试过的 NAPI / GRO 旋钮效果都在噪声内，需要更根本的手段。**

## 七、测量口径速查（做任何吞吐/CPU 测量前对照）

```sh
# 瞬时吞吐（唯一正确口径）
mbps = (bytes_now - bytes_prev) * 8 / 1000000 / (uptime_now - uptime_prev)

# 四核合计占用（核，满载 = 4.00）
# 必须含 irq + softirq，分母用实测间隔
busy_cores = (busy_now - busy_prev) / 100 / (uptime_now - uptime_prev)
# 其中 busy = /proc/stat 的 $2+$3+$4+$7+$8 (user+nice+system+irq+softirq)

# daed CPU（核）
daed_cores = Σ(每线程 utime+stime 增量) / 100 / 实测间隔
# /proc/PID/task/*/stat 的 $14+$15（去掉 comm 括号后是 $12+$13）

# 是否真走代理
cat /sys/class/net/dae0/statistics/rx_bytes    # 增长 = 走代理；为 0 = 直连/NPU

# 内核时基
awk '{print $1}' /proc/uptime                  # 开机秒数，精度 10ms
```

**正确与错误的判读对照：**

| 观察 | 错误结论 | 正确结论 |
|---|---|---|
| 崩塌时 CPU 空闲 | 设备无辜，瓶颈在上游 | 上游断流后**任何**设备都空闲，这是结果不是证据 |
| 没有单核 100% | CPU 没吃满 | 看**四核合计**，3.86/4.00 即满载 |
| 吞吐从 960 掉到 166 | 掉速 | 先还原累计字节 —— 可能只是没数据了 |
| 四核合计 > 4.00 | 设备很强 | **公式错了**，分母用了名义间隔 |

## 八、剩余可探索方向（按预期收益排序）

### 1. `daed-kdae`（Rust 重写版）vs rust daed 的每核效率对比 ← 唯一未验证的主要方向

**动机**：当前设备运行的是 `daed-kdae`。若 rust daed 的每核效率显著更高，
4 核上限可能从 550 提升到 700+（但仍达不到 1000）。

**判据**：同样负载下 `daed_cores` 与吞吐的比值（Mbps/核）。
本报告已建立可重放的测量方法（见第七节），可直接复用。

**风险**：切换 daed 会断网数十秒（daed **不是** fail-open 的服务级实现 ——
停止 `/etc/init.d/daed` 会断全屋）。回滚路径：
`/rom/usr/bin/daed`、`XR1710G/rustdaed-backup-before-kdae.tar.gz`、
`/etc/apk/arch.bak-kdae`。

### 2. 降低软中断的 40,000 周期/包

已试无效：`dev_weight` 64→256、`dae0` GRO/GSO/TSO on。
未试：`net.core.netdev_budget_usecs`、`rps_flow_cnt` 调整、eBPF 程序本身的批处理。

### 3. 换更省 CPU 的代理架构

例如内核态 TPROXY + 更轻量的转发路径。但加解密无法卸载，
预期收益有限，且改动面大、风险高。

### 4. 接受现状

**代理 550 Mbps / 直连 1000 Mbps** 对绝大多数家庭场景足够
（4K 流媒体约 25 Mbps，8K 约 100 Mbps）。

## 十、工具与环境陷阱（本轮新增，全部实际付过代价）

1. **`pkill` 在本设备不存在（BusyBox）**，且 `2>/dev/null` 会**静默**吞掉
   "command not found"，让你以为杀干净了。用显式 PID。

2. **★★ 绝不要按 cmdline 模式批量杀进程。**
   本轮我用 `awk '/while :/{print $1}'` 清理自己起的忙循环，结果：
   - **没杀到目标** —— `( while : ; do : ; done ) &` 创建的子 shell
     **继承了父脚本的 cmdline**（`sh /tmp/d6.sh`），pattern 匹配不到；
   - **误杀了系统进程** —— 兜底 pattern 扫到了
     `/bin/sh -c while true; do /usr/bin/ucode /usr/sbin/wifihistory; sleep 30; done`。
     （这次侥幸自愈：`/etc/rc.d/S99wifihistory` 由 procd 托管，已自动重启。）

   **⇒ 一律按确切 PID 操作，或先 `ps w` 人工确认。**

3. **PowerShell 哈希表键大小写不敏感** —— `@{ MBps=...; Mbps=... }`
   会报 `DuplicateKeyInHashLiteral`，因为两个键被视为同一个。

4. **PowerShell 会把 `$(...)` 在本地求值**、`<` 触发重定向拦截 —— 
   含这两者的 shell 一律整段 base64 传输。

5. **`/proc/net/snmp` 的 Tcp 段字段序号**（1-based，`$1="Tcp:"`）：
   `$11=InSegs $12=OutSegs $13=RetransSegs $14=InErrs $15=OutRsts`。
   **`$9` 是 EstabResets，不是 OutSegs** —— 取错列会得到无意义的数。
   取完必须做正向对照（造流量看列是否增长）。

6. **`/proc/stat` 的 cpu 行**：`$2=user $3=nice $4=system $5=idle $6=iowait $7=irq $8=softirq`。

## 十一、残余不确定性

**唯一未验证项**：`daed-kdae` 与 rust daed 的每核效率差异（第八节方向 1）。

**本判断的否证条件**：
若切回 rust daed 后，在同样负载下 `daed_cores` 显著下降
（例如同样 500 Mbps 只用 0.7 核而非 1.4 核），
则「4 核 A53 算力决定上限」的结论需要修正为「kdae 实现效率不足」，
4 核上限应相应上调。

**已确认不受本结论影响的部分**：直连 960 Mbps、NPU 卸载正常、
`netdev_budget` 修复、RPS/IRQ 均衡 —— 这些与代理上限无关，均已独立验证。
